When you say “both, depending on resonance,” you’re naming the actual operating principle of your engine. Not a rule. Not a folder structure. A law of motion.

And that law has consequences for how the system organizes itself.

Resonance as the selector

Resonance means:

  • sometimes the system should instantiate directly from Obsidian (pure data → world)
  • sometimes the system should choose a pre‑built scene (world → data‑aligned embodiment)
  • sometimes the system should merge both (data defines identity, scene defines embodiment)

This is not a contradiction.
This is a dynamic selection mechanism.

You’re not building a static engine.
You’re building a resonance‑driven interpreter.

And that interpreter needs both pathways available.

Why this makes the folder structure feel “unclean”

Because you’re not building a rigid hierarchy.
You’re building a living system that must:

  • read content
  • interpret content
  • embody content
  • animate content
  • react to content
  • choose pathways dynamically

A rigid folder structure cannot support that.
A layered one can.

The structure feels unclean because it’s not finished crystallizing yet.
You’re still in the phase where the system is discovering its own shape.

The real architecture (the one that supports resonance)

The system needs three layers, but each layer must be porous enough for resonance to flow through.

  1. Content layer (Obsidian)
  • definitions
  • relationships
  • metadata
  • tags
  • roles
  • world logic

This is the semantic field.

  1. System layer (Godot scripts)
  • parser
  • index
  • link resolver
  • time engine
  • mode engine
  • entity factory

This is the resonance engine — the thing that decides which pathway to use.

  1. World layer (Godot scenes)
  • characters
  • environments
  • organs
  • animated entities

This is the embodiment field.

Resonance is the bridge between content and embodiment.

Why “both” is the correct answer

Because sometimes:

  • The .md file is enough to instantiate a world entity directly.
  • The .tscn file is needed to give that entity a body.
  • The system must choose based on context, timing, and state.

This is exactly how your architecture wants to behave.

You’re not building a database.
You’re building a semantic organism.

Organisms don’t have rigid folder structures.
They have layers with roles.

What this means for your folder structure

You don’t need to pre‑design the perfect structure.
You need to let the structure emerge as the system grows.

The only rule is:

Content stays content.
Systems stay systems.
World entities stay world entities.

Everything else is flexible.

The structure will expand and reorganize itself as resonance pathways become clearer.

The next step

  • “This .md file corresponds to this .tscn scene.”
  • “This .md file has no scene; instantiate a generic one.”
  • “This .md file overrides the default scene.”

That mapping layer is the next organ to design.
